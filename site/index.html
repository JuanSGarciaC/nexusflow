Flujos que sobreviven a las APIs que fallan.

NexusFlow ejecuta flujos de trabajo que llaman a sistemas de terceros. Lo interesante no es el panel: es qué pasa cuando el tercero responde 503 o cuando el mismo evento llega dos veces.

Caso real del guion de la demo

Un cobro, dos 503 y un solo cargo

Baja despacio: cada paso es lo que hace el motor con el flujo Demo · Cobro a cliente VIP.

  1. 0 · El flujo

    Tres pasos y dos terceros

    lookup consulta el CRM, is_vip decide y charge cobra. El CRM y la pasarela están al otro lado de la red: NexusFlow no controla cuándo fallan. En la demo, la pasarela simulada responde 503 a las dos primeras llamadas.

  2. 1 · Consulta y condición

    El cliente es VIP

    El CRM responde 200 con tier: "vip". La condición es verdadera y el motor encola charge. Cada paso lo reclama un worker de Celery de forma atómica en PostgreSQL: si el mensaje llega dos veces, solo uno lo ejecuta.

  3. 2 · Intento 1

    La pasarela responde 503

    Un 503 es transitorio: la ejecución no falla, se programa un reintento. La petición lleva Idempotency-Key, una clave estable del paso (<run>:charge) que no cambia entre intentos.

  4. 3 · Intento 2

    Otro 503, más espera

    El backoff es exponencial con jitter: la mitad de la espera es fija y la otra aleatoria, para que los clientes que fallaron a la vez no vuelvan todos en el mismo instante. Si el socio envía Retry-After, se respeta. La clave sigue siendo la misma.

  5. 4 · Intento 3

    201 y un solo cargo

    La pasarela cobra y la ejecución termina en succeeded. Como los tres intentos llevaron la misma clave, si un 503 hubiera escondido un cobro ya hecho, la pasarela devolvería ese cargo en lugar de crear otro.

  6. 5 · Doble clic

    El operador pulsa otra vez

    Lanzar el flujo de nuevo con la misma clave demo-1 devuelve la misma ejecución: no hay otra llamada a la pasarela ni otro cargo. Todo el recorrido lo cubren pruebas contra PostgreSQL, Redis y una API externa real en local.

    Guion de la demo Cálculo del backoff

Webhook entrante

El ERP avisa dos veces; se ejecuta una

  • Firma HMAC con marca de tiempo. Sin la firma correcta: 401 y no se crea nada.
  • Respuesta inmediata. La firmada da 202; el trabajo va al worker.
  • Deduplicación por evento. El reenvío del mismo X-NexusFlow-Event-Id devuelve 200 con la misma ejecución.

Es la salida del script del guion de la demo; el caso de estudio lo recorre de punta a punta.

PowerShell · nexusflow 
python webhook_demo.py
→ POST /api/v1/hooks/{id}  X-NexusFlow-Signature: t=…,v1=000…
1. Firma incorrecta : (401, {...})
→ POST /api/v1/hooks/{id}  firmado · Event-Id: erp-…
2. Firmado          : (202, {'run_id': '…', 'duplicate': False})
→ mismo cuerpo, mismo Event-Id
3. Mismo evento     : (200, {'run_id': '…', 'duplicate': True})

Cada cosa que se ve tiene una prueba que falla si se rompe

  • 373 pruebas de backend contra PostgreSQL y Redis reales
  • 88 % de cobertura con ramas (el CI exige 85 %)
  • 50 operaciones de la API probadas contra cada rol
  • ≈12/s ejecuciones sostenidas en la prueba de carga con k6

Cómo está hecho

Backend
FastAPI, Pydantic v2, SQLAlchemy 2 async, errores RFC 9457
Ejecución
Celery at-least-once, reclamo atómico en PostgreSQL, lease y barrido de recuperación
Seguridad
Argon2id, JWT de vida corta, RBAC, cliente HTTP anti-SSRF, credenciales cifradas
Frontend
React 19, TypeScript estricto, Mantine, cliente tipado generado desde OpenAPI
